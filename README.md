# 智行 · 车内交互终端 Demo

---

## 快速开始

```powershell
# 1. 安装依赖（首次）
pnpm install

# 2. 一键启动（后端网关 + 业务进程 + 前端）
pnpm dev
```

然后打开 **http://127.0.0.1:5173**

| 地址 | 说明 |
| --- | --- |
| http://127.0.0.1:5173 | 车机界面（推荐 1920×1080 横屏窗口，按 F11 全屏） |
| http://127.0.0.1:5173/ops | 演示控制台：调仿真倍速、重开行程、注入车辆行为、看数据落库 |
| http://127.0.0.1:8080 | 网关（`/api/**` 全部转发到 :8081），根路径有导航页 |

**第一次打开会看到什么**：一辆车正在往你的上车点开过来（实测 4 倍速约 16 秒到达），
然后进入欢迎页 → 输入手机尾号 → 确认出发 → 行程开始，地图上车在真实路网上跑。
上车校验的 4 位码固定是 **`1234`**（默认乘客林小满 `13800001234` 的手机尾号，
写在 `backend/src/infra/seed.service.ts` 的 `DEMO_VERIFY_CODE`），不用去数据库里查。

## 演示动线（建议按这个顺序走一遍）

1. **车辆来接**（`/waiting`）：地图上车辆正在靠近，实时位置与所在道路都在动
2. **欢迎上车**（`/welcome`）：核对车牌与车内编号，这是"一单一车"场景里最重要的一次确认
3. **身份校验**（`/verify`）：只能用屏幕数字键盘，输入手机号后 4 位
4. **出发确认**（`/ready`）：系好安全带等三项检查，然后按下「开始行程」
5. **行程中**（`/trip`）：**产品最核心的一屏**。左侧常驻行程卡 + 全屏自绘地图 + 决策气泡。
   车辆每次礼让行人、等待信号灯、绕行障碍物，屏幕都会用一句人话解释它在干什么
6. **旅程解释**（`/trip/explain`）：这趟行程的时间都花在哪了（ECharts 堆叠条 + 行为时间线）
7. **环境控制**（`/cabin`）：一键场景（小憩 / 办公 / 放松 / 舒缓），温区、风量、座椅、氛围灯、遮阳帘
8. **停靠**（`/stop`）：常用下车点一键请求；紧急停车需要长按 1.2 秒
9. **帮助**（`/help`）：高频问题、接通远程安全员、隐私与设备状态说明
10. **即将到达**（`/arriving`）→ **下车**（`/alight`）：车未停稳时开门按钮会禁用并说明原因
11. **行程小结**（`/summary`）：速度曲线 + 费用构成（ECharts）
12. **评价**（`/rate`）→ **送别**（`/farewell`）：告知个人数据已从这块屏幕上清除

想快速看到后半段，直接在 `/ops` 点「跳到即将到达」。

## 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3.5 + Vite 8 + TypeScript + Pinia + Vue Router | 纯 CSS + 设计令牌，不用 UI 框架的默认观感 |
| 图表 | ECharts 6（`echarts/core` 按需引入 + 自定义 ToC 主题） | 去网格线、去 legend、直接标注 |
| 地图 | **自绘矢量路网**（Canvas 2D） | 离线可用；前后端共用同一份 `assets/map.json` |
| 实时 | SSE | 车辆位置 2Hz 推送，前端按 60fps 插值补间 |
| 后端 | NestJS 12 + Fastify 5，`tsc` 编译后用原生 node 运行 | 网关独立进程 + 业务域聚合多模块，共 2 个进程 |
| 数据库 | **SQLite，走 Node 24 内置 `node:sqlite`** | 零安装、零原生编译，单文件 `backend/data/robotaxi.db` |
| 设计资产 | taste-skill（MIT） | 见 `skills/`，仅取设计规则，不套用其页面骨架 |

**核心亮点**：后端内置**车辆仿真引擎**（合成路网 + Dijkstra 寻路 + 500ms 仿真时钟 + 可调倍速），
车辆真的沿路网行驶，并沿途产生"决策行为"事件流，驱动前端的决策可视化。

## 常用命令

```powershell
pnpm dev                 # 一键启动（后端 + 前端）
pnpm dev:backend         # 只启动后端（gateway:8080 + app:8081）
pnpm dev:frontend        # 只启动前端（:5173）
pnpm typecheck           # 前后端类型检查
pnpm seed                # 重建演示数据（--force 清库重来）
pnpm reset:db            # 删除 SQLite 文件，下次启动自动重建
pnpm gen:map             # 重新生成路网（改完 assets/map.json 后前后端同时生效）

pnpm test:api            # 端到端接口自测：从"车辆来接"一路跑到"行程小结"
pnpm test:ui             # 渲染走查：真浏览器跑完 21 屏，顺带导出截图
pnpm test:ui-audit       # 界面体检：量对比度、触控尺寸、溢出、圆角、画布
pnpm check               # 上面四项全跑一遍
```

**三层验证，各自负责不同的问题**：

| 脚本 | 回答什么问题 | 现状 |
| --- | --- | --- |
| `smoke.mjs` | 业务链路和接口契约对不对 | 43/43 |
| `ui-walkthrough.mjs` | 19 个页面在真浏览器里能不能渲染出来、该跳的跳不跳 | 53/53 |
| `ui-audit.mjs` | 渲染出来的东西**是否可读、可点、不破版** | 22 屏 0 项待处理 |

`ui-walkthrough.mjs` 会把每一屏截图写到 `.walkthrough/`，可以直接当作 Demo 的界面预览。
注意这些截图是**跑一次就重新生成一次**的：状态条上的时间每次都不同，所以跑完走查后
`git status` 会显示 21 张图片有改动，这是预期的，不是界面变了。
`ui-audit.mjs` 不截图，它在真实渲染的页面上量尺寸：文本与背景的对比度（WCAG AA）、
触控目标是否够大、有没有内容被裁掉或横向溢出、圆角是否只用令牌里的那几档、
以及 Canvas 是否真的画出了东西（图表走空状态时 DOM 看起来是正常的，只有数画布才发现得了）。
它按状态机的顺序分 6 个阶段推进后端（等车 → 核对身份 → 出发确认 → 行程中 → 到达下车 → 收尾），
因为这 19 屏并不是在任何状态下都同时存在；浅色主题另外抽查 3 屏，
所以总数是 22 屏。改完某一屏想单独复检，可以在命令后面直接跟路由，例如：

```bash
node scripts/ui-audit.mjs /summary /cabin
```

## 环境要求与已知限制

| 依赖 | 要求 | 本机实测 |
| --- | --- | --- |
| Node.js | ≥ 22（需要内置 `node:sqlite`） | v24.21.0 ✅ |
| pnpm | ≥ 9 | 11.7.0 ✅ |

**网络**：本机直连 `registry.npmjs.org` 只有 20~40 KiB/s，安装 echarts / typescript 这类大包必然超时。
项目根目录的 `.npmrc` 已固定使用 `registry.npmmirror.com`（实测快约 100 倍），**不要改回官方源**。

**为什么后端用 `tsc` 编译而不是 `tsx` 直接跑 TS**：
NestJS 的依赖注入依赖 TypeScript 的 `emitDecoratorMetadata` 产出 `design:paramtypes`，
而 esbuild（tsx 的底层）明确不支持该能力，会导致所有构造器注入拿到 `undefined`。
所以启动流程是 `tsc` 编译一次 → 原生 node 跑 `dist/`，顺带也更快。

**走查偶发失败时先清 Vite 的预构建缓存**：
改过依赖（增删 `package.json` 里的大包）或者移动过项目目录之后，
`frontend/node_modules/.vite` 里缓存的依赖预构建结果会跟实际依赖对不上，
表现是某些懒加载的路由 chunk 迟迟不落地，某个页面看起来"渲染了个空壳"。
清掉它再重启即可，这不是代码问题：

```bash
rm -rf frontend/node_modules/.vite && pnpm dev
```

## 设计原则（不可协商）

1. **这是给乘客用的产品，不是给运营用的后台。**
   禁止左侧导航栏、面包屑、三栏后台壳、DataTable、筛选行 + 汇总 + 表格、KPI 数字墙、饱和色状态标签。
2. **全局只有一个强调色**（柔蓝）。成功 / 警告 / 危险是语义色，只小面积使用。
   层级靠 1px 描边与亮度差，不靠重投影（深色下几乎不用阴影）。
3. **实时感是这个 Demo 的命门。** 车辆必须沿真实路网移动并被前端平滑插值渲染，静止的图标等于 PPT。
4. **车内的第一功能是"解释"。** 乘客坐在没有司机的车里，最大的焦虑是"它刚才为什么那样开"，
   所以每次车辆行为变化都要给一句人话解释（决策气泡 + 旅程解释）。
5. **安全操作要能被误解地防御。** 车没停稳时开门按钮必须禁用**并说明原因**；
   紧急停车用长按 1.2 秒而不是弹窗；帮助从任何页面一次点击可达。
6. **公共设备的数据纪律。** 不做登录，会话与行程绑定；行程结束即失效，送别页明确告知数据已从屏幕清除。

### 渲染走查与体检发现并修掉的问题

这些都不是"看起来还行"就能发现的，是量出来的：

| 问题 | 后果 | 处理 |
| --- | --- | --- |
| 次要文字色 `#6c7686` 对底色只有 **3.44:1** | 13px 的说明文字在车里根本读不清，每屏 18 处不达标 | 深色改 `#828d9e`（4.7:1）、浅色改 `#5c6472`（4.9:1） |
| 状态条工具按钮只有 34×34 | 触摸屏上必然误触 | 放大到 44×44，并在样式里显式标注为豁免档 |
| 「这趟车都经历了什么」按钮高度只有 17px | 一条长得像说明文字的可点行，几乎点不到 | 给到 56px 触控高度 |
| 圆角出现 11/12/13/14/16px 五档野值 | 视觉上立刻显脏 | 收敛到 `--r-input` / `--r-btn` 令牌 |
| 开门瞬间后端没把车速归零 | 状态已是"已到达"但开门报错；若仿真恰好在那一刻暂停，**车门将永远打不开** | 在到达的那一刻就归零并广播 |
| 行程结算用**墙上时钟**算时长 | 16 倍速仿真下 4.7 公里被算成平均 **1539 km/h**、总时长显示 1 分钟，时长费也是错的 | 时长按仿真里程占比折算，回到 28 km/h |
| 「跳到即将到达」不补轨迹采样 | 演示最常用的近路会让小结页的速度曲线空掉 | 快进时按路段限速补齐采样点 |
| 走查按固定 sleep 等图表 | 误报（图表在下一帧才建 canvas） | 改成轮询等画布出现，超时才失败并打印页面文字 |
