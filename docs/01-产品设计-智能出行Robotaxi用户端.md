| # | 决策项 | 结论 | 理由 |

| D1 | 后端技术栈 | **NestJS 12 + Fastify + TypeScript**（Node.js v24） | 本地项目、无高并发诉求，Node 后端足够且开发链路统一（前后端同语言）；NestJS 的模块 / DI / Guard / Interceptor 与微服务分层一一对应，是 Node 生态里最"主流微服务框架"的选择。**已实测：本机 `java`、`mvn` 均未安装，Node v24.21.0 / npm 11 / pnpm 11 可用** |
| D2 | 架构形态 | **网关独立进程 + 业务域聚合单体多模块**：`gateway`(:8080) + `app`(:8081) 两个进程，业务域以 NestJS Module 组织 | 兼顾"微服务的架构表达"与"本地一键启动的开发体验"，两个进程即可完整演示 |
| D3 | 首版范围 | **M0 + M1**：先打通「下单 → 派单 → 车辆实时靠近 → 上车 → 行程 → 结算」主链路 + 车辆仿真引擎，视觉先用基础样式 | 实时主链路是最大技术风险，必须先验证；视觉打磨放在 M2 |
| D4 | 地图实现 | 自绘矢量路网（离线、风格统一、前后端共用 `map.json`） | 无需 Key、不怕断网、动效可控 |
| D5 | 数据库 | **SQLite，通过 Node 24 内置的 `node:sqlite`（`DatabaseSync`）**，单文件 `backend/data/robotaxi.db` | **零依赖零安装**：不需要装任何数据库软件，也不需要原生编译（已实测 `node:sqlite` 在本机 v24.21.0 下 ESM 可用）。不选 better-sqlite3 是因为它是原生模块，Node 24 上可能没有预编译二进制，会触发 node-gyp 编译（正是要避免的"下载一堆东西"） |
| D6 | 服务注册发现 | 不引入注册中心；网关路由表写在配置里 | 两个进程，注册中心无收益 |
| D7 | 业务控制台 | 做极简 `/ops` 页面（造拥堵/故障场景 + 数据重置），**不做任何后台管理风格界面** | 演示时可现场制造场景，是讲故事的关键道具；但必须与用户端共用同一套 ToC 视觉语言，禁止 DataTable + 侧边栏那一套 |
| D8 | 前端图表 | 用 **ECharts 6**，但必须做「ToC 化」主题改造，禁止默认后台报表样式 | 详见 `02-前端设计规范-ToC风格与图表指南.md` |
| D9 | 视觉风格 | **ToC 消费级产品观感，明确禁止后台管理风格**；引入 `taste-skill` 设计技能约束 AI 产出 | 详见 `02` 与 `03` 文档；skill 已下载到 `robotaxi-demo/skills/` |

> 后续若要拆成"更纯粹的微服务"（拆进程 + 消息队列），因为 NestJS Module 边界已经切干净，改造成本集中在 `main.ts` 与传输层配置，业务代码不动。
> 后端由 Spring Cloud Alibaba 改为 NestJS 的原因：本地 Demo 无高并发诉求 + 本机无 JDK/Maven + 前后端同语言可降低维护成本。此变更已记录在决策表内，不再保留旧方案文档。

## 1. 背景与目标

### 1.1 背景

无人驾驶出租车（Robotaxi，如萝卜快跑、小马智行、Waymo One）已经从测试走向部分城市常态化运营。相比传统网约车，它改变了三件事：

1. **没有司机** —— 用户失去「和司机沟通」这个信息通道，所有不确定性必须由产品界面来消化（车在哪、为什么停、怎么上车、出问题找谁）。
2. **车是「公共运力」** —— 车辆调度完全由系统决定，用户能感知的是「匹配速度」和「价格透明度」。
3. **安全语义变了** —— 用户面对一台没有人的车，需要额外的信任设计（远程安全员、行程分享、一键求助、车内可视）。

### 1.2 Demo 目标

我们要做的不是「能跑通的 CRUD 后台」，而是一个**看起来像真产品、点得下去、有实时感**的用户端站点。三条验收线：

- **好看**：进首屏 3 秒内让人相信这是一个真实运营的产品级界面，而不是课程作业。
- **真实**：叫车 → 派单 → 车辆在地图上开过来 → 上车 → 行程中 → 到达支付，全链路可走通，车辆位置是**真实移动的**（后端仿真推送）。
- **有亮点**：至少 3 个能讲的差异化功能（智能目的地推荐、全程可信可视化、AI 出行助手/远程协助）。

### 1.3 非目标（本期不做）

- 不做真实地图路径规划（用仿真路网 / 简化路径）、不接真实支付、不接真实无人车。
- 不做多城市、多租户、司机端 App。
- 不做完整运营中台（仅保留一个极简「仿真控制台」用于驱动 Demo）。

## 2. 产品定位

> **一句话定位**：一个让普通人敢坐、爱坐无人驾驶出租车的出行入口 —— 打开就能叫到一台没有司机、但全程看得见、随时有人管的车。

### 2.1 与传统网约车的差异化主张

| 维度 | 传统网约车 | 智行 Robotaxi |
| --- | --- | --- |
| 接驾沟通 | 电话/IM 和司机确认 | 系统引导：3D 上车点指引 + 车辆灯光/鸣笛指令 + 解锁码 |
| 行程体验 | 取决于司机 | 标准化：可自选温度、音乐、路线偏好，无社交压力 |
| 安全感来源 | 司机本人 | **可信可视化**：实时轨迹、车内状态、远程安全员、行程分享、紧急联系人 |
| 价格 | 动态加价不透明 | 一口价 + 费用明细 + 预估价格锁定 |
| 覆盖 | 全时段 | 展示运营区域（ODD）边界，明确「哪里能去、什么时候能去」 |

### 2.2 安全与信任是核心设计命题

无人车产品的用户端，本质上是一个**信任界面**。以下设计贯穿全场：

- **看得见**：车在哪、还有几公里、车在做什么决策（如"正在等待行人通过"）→ 用状态文案而不是裸进度条。
- **有人管**：任何页面 1 次点击可达「客服 / 远程协助」，行程中长按可触发 SOS。
- **可回溯**：行程结束后可查看完整轨迹回放、车内外录像（Demo 用占位图 + 时间轴模拟）。
- **可退出**：行程中随时可以「我要下车 / 改成人工接管」——即便是演示，也要让用户看到这个入口。

## 7. 关键用户旅程

### 7.1 主流程（Happy Path）

```
打开首页
 → 定位到"当前位置"，地图上一个脉冲点 + 周边 3 台空闲无人车（缓慢巡航动画）
 → 输入/选择目的地（或点智能推荐卡片"回家 · 预计 12 分钟 ¥18"）
 → 底部抽屉展开：3 个车型卡 + 一口价 + 预估到达
 → 点击"呼叫无人车"
 → 匹配中：雷达扫描动效，显示"正在为你匹配最近车辆…"（3~8s）
 → 匹配成功：车辆卡片 + 地图上车辆开始沿路网驶向上车点，倒计时 4 分钟
 → 车辆到达：提示"车辆已到达，请前往上车点（前方 30m，看到尾号 3721 的车）"
 → 输入解锁码 3721 / 点"一键开门" → 车门动画 → 上车
 → 行程中：地图跟随、进度条、剩余时间/费用；可调空调/音乐，可分享行程
 → 到达：车辆靠边停稳 → 自动结算 → 费用明细 + 行程报告 → 评价
```

### 7.2 异常流程（体现产品思考，用于 Demo 讲故事）

| 场景 | 产品处理 |
| --- | --- |
| 上车点不能停车 | 自动纠偏并说明原因，给"重选上车点"入口 |
| 车辆因障碍物延迟 | 主动推送原因 + 补偿优惠券 |
| 用户想中途下车 | 选择下车点 → 重新计价 → 安全提示 |
| 用户感到不安全 | 一键呼叫远程安全员 / SOS 长按 3 秒 |
| 运营区域外目的地 | 提示"该目的地超出无人驾驶运营范围"，推荐邻近可停点 |
| 匹配超时 | 排队序号 + 预计等待 + 转其他车型建议 |

## 8. 视觉与交互设计规范

> 本章是**摘要与约束**；完整细则、ECharts 主题代码、Pre-Flight 检查清单见 **`02-前端设计规范-ToC风格与图表指南.md`**。
> 本章规则与 `taste-skill`（见 `03` 文档）对齐，冲突时以 `02` 为准。

### 8.1 设计读法与三个旋钮

按 taste-skill 的要求，动手前先给出**一行 Design Read**，再设定三个旋钮：

> **Reading this as: 面向大众乘客的 ToC 出行产品（非营销落地页、非后台），语气"premium consumer + trust-first"，倾向自绘矢量地图 + 克制的高级消费电子语言。**

| 旋钮 | 取值 | 说明 |
| --- | --- | --- |
| `DESIGN_VARIANCE` | **7** | 消费级产品要有设计感，但功能型页面不能乱（比落地页的 8 低一档） |
| `MOTION_INTENSITY` | **6** | 车辆移动、状态切换必须有动效；但禁止无意义的循环微动效 |
| `VISUAL_DENSITY` | **4** | 留给地图呼吸空间；信息密集页（订单详情）可临时到 5 |

> 安全中心、SOS、紧急联系人页**单独降档**为 `3 / 2 / 5`：trust-first 场景下克制与清晰压倒设计感。

### 8.2 色彩（一页一 accent）

**核心纪律：全站只有 1 个 accent 色。** 主色之外的青绿/橙色只作为**语义色**（成功 / 警示），不承担"第二品牌色"的角色，也不允许大面积使用。

| 角色 | 浅色模式 | 深色模式 | 用途 |
| --- | --- | --- | --- |
| **Accent（唯一）** | `#2F6BFF` 电光蓝 | `#5B8CFF` | 主按钮、路径线、选中态、关键数字 |
| 语义 · 成功 | `#00A88F` | `#2ED3BC` | 车辆已到达、支付成功（仅小面积图标/文字） |
| 语义 · 警示 | `#D9642F` | `#FF9466` | 价格变动、延误提示（仅小面积） |
| 语义 · 危险 | `#D93A3C` | `#FF6B6D` | SOS、取消 |
| 背景 BG | `#F6F8FB` | `#0E1116` | 页面底（**深色模式禁用纯黑 `#000`**） |
| 卡片 Surface | `#FFFFFF` | `#171B22` | 卡片、抽屉 |
| 文字 主/次/辅 | `#141A24` / `#5A6472` / `#98A2B3` | 反相 | 层级 |

**硬性约束**（来自 taste-skill）：

- 饱和度默认 < 80%，accent 之外的色一律低饱和。
- **禁止 AI 紫**、禁止霓虹外发光、禁止纯黑。
- **Color Consistency Lock**：accent 一旦定下，全站（含图表、地图、图标）统一使用，不允许某个页面突然出现一个青色 CTA。
- **Shape Consistency Lock**：圆角只允许一套规则，本项目定死为 **按钮=全圆角胶囊 / 卡片=20px / 输入框=12px / 抽屉顶部=28px**，不得混用。

渐变仅允许出现在两处：首页叫车主按钮的极淡渐变、匹配中的雷达动效。**克制使用渐变是"看起来贵"的关键。**

### 8.3 字体与排版

- 中文正文：`PingFang SC` → `HarmonyOS Sans` → `Microsoft YaHei` 兜底。
- 拉丁/数字：**`Geist` + `Geist Mono`**（skill 明确不建议把 Inter 当默认；数字用等宽字形避免倒计时与价格跳动）。
- 字号阶梯（移动端为主）：`12 / 14 / 16 / 20 / 24 / 32 / 40`；正文行高 1.5，标题 `leading-none` + `tracking-tight`。
- 正文宽度上限 `65ch`；卡片内文案不超过 3 行。
- **大数字是视觉锚点**：价格、倒计时、剩余里程用 32~40px 半粗 + 等宽数字。
- 强调同一标题内的词用**同字族的 bold / italic**，禁止在无衬线标题里混一个衬线词。

### 8.4 地图视觉

- 主方案：**自绘矢量城市路网**（SVG/Canvas，完全掌控配色与动效，离线可用、加载瞬时）；路网浅灰蓝描边、主路加深，公园/水系用低饱和色块。
- 地图配色必须服从 §8.2 的色板：路线用 accent 蓝，车辆状态用语义色，禁止在地图上用一套独立的"地图配色"。
- 车辆图标：圆角矩形车形 + 柔和光晕；朝向随行进方向旋转；空闲车半透明巡航，接驾车辆实心 + 轨迹线。
- 备选方案：接入 Mapbox / 高德 JS SDK（需 Key、联网，且视觉受底图限制，与 §12 "离线可运行"要求冲突，仅作备案）。

### 8.5 动效清单（`MOTION_INTENSITY: 6`）

| 位置 | 动效 |
| --- | --- |
| 首页进入 | 地图从 1.05 缩放淡入（400ms `cubic-bezier(.22,1,.36,1)`）+ 卡片自下而上弹出 |
| 车辆移动 | 沿路径插值 + 转弯时轻微 rotate 缓动，避免生硬直角 |
| 匹配中 | 雷达波纹 + 车辆图标在周边闪现 |
| 派单成功 | 卡片"锁定"回弹 + 车辆高亮脉冲 |
| 到达 | 车辆停稳后卡片变绿 + 轻微震动（`navigator.vibrate`，移动端） |
| 价格数字 | 数字翻滚（count-up，等宽数字） |
| 页面切换 | 底部抽屉式滑入 + 共享元素过渡（车辆卡片 → 行程页） |
| 骨架屏 | 所有网络请求均有 Skeleton，禁止整页转圈 |

**动效禁令**：禁止 `linear` / `ease-in-out` 这类"默认缓动"、禁止无意义的无限循环微动效、禁止自定义鼠标指针、禁止滚动提示（"Scroll to explore"）与装饰性呼吸点。必须响应 `prefers-reduced-motion`。

### 8.7 图表规范（ECharts 6）

> 完整主题代码与各图表配置见 `02` 文档第 4 章。这里只写不可违背的结论。

**定位**：图表在本产品里是**给用户看自己的出行故事**，不是给运营看的数据看板。因此：

- 允许出现图表的位置：**出行足迹 `/me/stats`、行程报告 `/ride/settle` 与 `/orders/:id`、首页"错峰可省 ¥X"小提示**。
- **禁止**出现图表的位置：任何以"数据汇总 + 筛选器 + 表格"形态出现的页面（那就是后台）。
- 硬性做法：去掉网格线与坐标轴线、坐标轴标签弱化到辅助文字色、用渐变面积替代实心色块、**不用 legend 而是直接在线条/区块上标注**、圆角柱、数值直接标注、配色只用 §8.2 定义的色板。
- 每页图表数量 ≤ 2，且必须有"这句图表说明了什么"的一句话结论文案。
- 图表必须动画入场（800ms `cubicOut`），并支持深色模式切换重绘。

### 8.8 反后台化守则（本节是红线）

**必须避免**（出现任意一条即视为风格跑偏）：

- ❌ 左侧竖向导航栏 + 顶栏面包屑 + 右侧内容区的三栏骨架
- ❌ 满屏 DataTable（带斑马纹、分页器、每列筛选、操作列"编辑/删除"）
- ❌ 顶部一整行筛选表单（"开始时间 / 结束时间 / 状态 / 查询 / 重置"）
- ❌ 全屏浅灰底 + 一堆白色方块卡片 + 卡片里再塞表格
- ❌ Element Plus / Ant Design 默认蓝 + 默认组件外观
- ❌ 右上角"管理员头像 + 退出登录"下拉
- ❌ KPI 数字墙（4 个巨型数字 + 同比环比箭头）
- ❌ 满屏彩色状态 Tag（"已完成/进行中/已取消"用高饱和底色铺开）

**应该这样做**：

- ✅ 底部 Tab 栏（移动端）/ 顶部极简胶囊导航（桌面端），导航项 ≤ 4
- ✅ 内容以**卡片流**或**时间轴**呈现，一屏一个焦点
- ✅ 地图作为背景层，业务信息用底部抽屉（Bottom Sheet）叠加
- ✅ 大圆角、柔和弥散阴影、充足留白
- ✅ 状态用**图标 + 文字色**表达，不用大面积色块
- ✅ 数字要有上下文（"12 次出行" 优于孤零零一个 "12"）
- ✅ 主操作热区落在拇指可达范围（屏幕下半部）

完整对照表与代码级细则见 `02` 文档第 3 章。

## 9. 数据模型（本地库设计）

数据库：**SQLite 单文件**（`backend/data/robotaxi.db`），由 **Node 24 内置的 `node:sqlite`** 直接读写。不需要安装任何数据库软件，`pnpm i` 也不会拉进任何数据库依赖，随进程启动即用。

> 每个域模块**逻辑上拥有自己的表前缀 / 独立 Repository**（Demo 共用一个 SQLite 文件），跨域只能通过 Module 导出的 Service 接口或领域事件获取数据，禁止跨模块直接查表 —— 这是"微服务边界"在单进程下的落地方式。
>
> ORM 取舍：默认**不引入 ORM**，用 `node:sqlite` 的 `DatabaseSync` + 一层薄 Repository（`prepare` / `all` / `get` / `run` + 手写行到对象的映射）。原因见 §10.4。若后期想要类型安全的查询构建器，可加 `sqlite-proxy` 驱动把 Drizzle ORM 架在 `node:sqlite` 之上（约 30 行适配代码）。

### 9.2 订单状态机（必须严格定义，前后端共用）

```
CREATED(已创建) 
  → MATCHING(匹配中) 
  → MATCHED(已派单/车辆前往中) 
  → ARRIVED(车辆已到达上车点) 
  → ONGOING(行程中) 
  → SETTLING(结算中) 
  → COMPLETED(已完成)
  
旁支：CANCELLED(已取消) / TIMEOUT(超时未上车) / EXCEPTION(异常中断)
```

每个状态迁移都向 `t_order_event` 写入一条记录，同时通过 SSE 推送给前端 —— 这既是业务逻辑，也是 Demo 的可视化素材。

### 10.2 服务（模块）划分

**形态：网关独立进程 + 业务域聚合单体多模块**（决策 D1/D2）。业务代码按 NestJS Module 严格分包，Module 之间只通过导出的 Service 接口或领域事件通信，禁止跨 Module 直接访问对方的 Repository —— 这样任何一天想拆进程，都能原地拆开。

| 模块 | 部署形态 | 职责 | 关键点 |
| --- | --- | --- | --- |
| `gateway` | **独立进程** :8080 | 路由、JWT 校验、CORS、限流、生产模式下托管前端产物 | 前端只调网关 |
| `app` | 独立进程 :8081 | 聚合启动器，装配全部业务 Module | 默认运行方式 |
| ├─ `auth` | Module | 登录、验证码、Token 签发与续期 | JWT 无状态 |
| ├─ `user` | Module | 用户资料、地址、紧急联系人、偏好 | |
| ├─ `order` | Module | 订单生命周期、状态机、行程轨迹 | 核心域 |
| ├─ `fleet` | Module | 车辆档案、车辆状态、POI/地图数据 | |
| ├─ `dispatch` | Module | 匹配算法、车辆移动仿真、仿真时钟 | **心跳模块** |
| ├─ `pricing` | Module | 一口价计算、优惠券、费用明细 | |
| ├─ `payment` | Module | 钱包、支付流水 | |
| ├─ `safety` | Module | 行程分享、SOS、紧急联系人通知 | |
| ├─ `notify` | Module | SSE 长连接推送、消息中心 | 前端实时感的来源 |
| └─ `ops` | Module | 仿真控制台接口、数据重置 | Demo 工具 |

**Module 间通信**：进程内使用 NestJS 的 `EventEmitter2`（`@nestjs/event-emitter`）发领域事件（`order.matched`、`vehicle.arrived`），监听方解耦；同步调用走 Module 导出的 Service。**事件模型与 MQ 语义一致，将来换成 Redis Streams / NATS / Kafka 只改传输层。**

> 若某天要拆进程：`gateway` 已独立；再把 `app` 按 Module 拆成多个 Nest 应用（`NestFactory.createMicroservice`），事件总线换成 MQ，业务代码不动。

### 10.3 实时通信方案

- **主方案：SSE（Server-Sent Events）**。出行场景是"服务端持续推、客户端只读"，SSE 比 WebSocket 更简单（原生 `EventSource`、自动重连、走 HTTP 便于网关统一鉴权）。
- 推送事件：`vehicle.position`、`order.status`、`trip.progress`、`notify.message`。
- 前端用一个 `useRealtime` composable 统一订阅 + Pinia 存储，组件只读 store。
- 若网关/浏览器有连接数限制问题，再退化为 1s 轮询（保证 Demo 永远不卡）。

### 10.4 数据库：本地免安装方案对比

前提约束：**不安装任何数据库软件、不引入需要原生编译的依赖**。

| 方案 | 需要安装/编译吗 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **`node:sqlite`（Node 内置）** | **都不用**，Node 24 自带 | 零依赖、同步 API 简单直接、单文件持久化、真 SQL、已实测本机可用 | 仍是 experimental 标记（功能稳定，会有 warning） | ✅ **采用** |
| better-sqlite3 | 可能要编译 | 生态最大、Drizzle 官方支持 | **原生模块**，Node 24 上若无预编译二进制会触发 node-gyp 编译，需要 VS Build Tools | 不采用（正是要避免的"下载一堆东西"） |
| libsql (`@libsql/client`) | 不用（有预编译包） | 无需编译、兼容 SQLite、可平滑上云 | 多一层依赖 | 备选（想要 ORM 时走这条） |
| PGlite（Postgres 编译成 WASM） | 不用 | 真 Postgres 语义 | 启动重、Demo 用不上 | 不推荐 |
| 纯 JSON 文件 / lowdb | 不用 | 最简单 | 无 SQL、无事务、说服力弱 | 不推荐 |

**实现约定**：

```ts
// backend/apps/app/src/infra/db/sqlite.service.ts
import { DatabaseSync } from 'node:sqlite';   // Node 24 内置，无需 npm 安装

const db = new DatabaseSync('data/robotaxi.db');
db.exec('PRAGMA journal_mode = WAL; PRAGMA foreign_keys = ON;');
```

- **建表方式**：按 Module 分目录维护 `.sql` 迁移文件（`src/modules/order/schema.sql`），启动时按顺序执行 + 一张 `schema_migrations` 表记录已应用版本。不引入 ORM/迁移框架。
- **主键与时间**：主键用自增 `INTEGER PRIMARY KEY AUTOINCREMENT`（订单号另生成可读业务号），时间统一存 **Unix 毫秒整数**（SQLite 没有原生日期类型）。
- **并发控制**：SQLite 单写者，Demo 内用 `BEGIN IMMEDIATE` 事务 + 业务层串行化（仿真时钟是单线程定时器，天然串行）；乐观锁用 `version` 字段。
- **缓存**：进程内 `Map` + 轻量 LRU 即可，**不引入 Redis**。
- **数据可见性**：提供一个只读的 `/ops/db` 页面用表格展示关键表行数与前 20 行，满足"数据真的落库了"的演示需求（注意：这是内部工具页，视觉上也不是后台管理风格，见 `02` 文档）。
- **数据重置**：`POST /api/ops/reset` 删表重建 + 重灌种子数据，保证演示前 1 秒回到干净状态。

### 10.5 车辆仿真引擎（Demo 能否"活起来"的关键）

这是整个 Demo 最有技术含量的部分，也是让页面不假的核心：

1. **路网数据**：手工定义一张小型路网（约 30~50 个节点、60~100 条边）用 JSON 描述，节点是路口、边是路段（含限速、方向）。前端与后端共用同一份 `map.json`，保证车辆位置与地图渲染完全对齐。
2. **仿真时钟**：`dispatch` 模块内一个 `setInterval`/`node:timers` 循环，每 500ms 推进一步，速度倍率可调（1x / 4x / 16x），使 Demo 的 10 分钟行程能在 40 秒内演完。
3. **车辆行为**：空闲车在随机边上巡航；被派单后用车端 A*/Dijkstra 计算到上车点路径并沿线行驶，速度按路段限速 + 随机扰动；到达后等待，行程中沿订单路径行驶。
4. **位置推送**：步进后通过 `EventEmitter2` 领域事件 → `notify` 模块 → SSE 广播；前端做插值渲染（在两次推送之间用 requestAnimationFrame 平滑补间，避免 500ms 一跳）。
5. **时间压缩的诚实处理**：UI 上显示"演示加速中 ×4"角标，避免观感上的逻辑矛盾。

## 14. 演示脚本（3 分钟讲故事）

1. **开场**：打开首页，地图上有 5 台无人车在巡航，"现在有 5 台车在您附近"。
2. **亮点 1**：对着助手输入"帮我叫一辆去公司的车，要安静、26 度" → 自动填充目的地、车型与偏好。

4. **实时感**：车辆沿真实路网开过来，卡片显示"还有 1.2 公里，约 3 分钟"，车辆转向时朝向跟随。
5. **上车**：提示"车辆已到达，尾号 3721" → 输入解锁码 → 车门开启动画。
6. **行程中**：展示决策气泡"正在礼让行人"；调低空调温度；点"分享行程"。
7. **亮点 2**：点击"呼叫远程协助"，安全员头像接入并回应（模拟），体现"没有司机也有人管"。
8. **亮点 3**：注入"前方拥堵"异常 → 卡片弹出解释 + 系统赠送 ¥5 券。
9. **收尾**：到达结算，费用明细 + 行程报告（3.2 公里、减碳 0.4kg、用时 11 分钟）+ 轨迹回放。

## 15. 风险与决策记录

### 15.1 已识别的风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 真实地图 SDK 需要 Key/联网/商用授权 | 演示可能失败 | 默认自绘矢量地图，SDK 作为可选插件 |
| 进程数量多导致本地启动慢/内存占用高 | 开发体验差 | ✅ 已定：聚合单体多模块，仅 2 个进程（gateway + app） |
| 车辆位置 500ms 一跳显得卡顿 | 观感差 | 前端插值补间（关键渲染细节） |
| **本机无 JDK / Maven；PowerShell 的 .NET HTTP 栈被拦截** | 后端无法启动 / 依赖装不上 | ✅ 已定改用 Node 后端（无需 JDK）；**网络操作一律走 Node/pnpm，禁用 `Invoke-WebRequest`**（已实测 `npm ping` 通、`codeload.github.com` 可访问） |
| ECharts / Naive UI 默认样式自带"后台味" | 风格跑偏，直接违背 ToC 要求 | 强制套自定义主题（`02` 文档第 4 章），并把「反后台化守则」列为验收红线 |
| AI 生成前端代码自带模板味（AI 紫渐变、三等分卡片、满屏 em dash） | 观感廉价 | 引入 `taste-skill` 约束产出，落地 Pre-Flight 检查清单（`03` 文档） |
| 中文路径 + Windows 编码问题 | 构建报错 | 工程目录用 ASCII 命名，源文件统一 UTF-8 |

### 15.2 决策结论（v0.3 已确认）

| # | 决策 | ✅ 结论 |
| --- | --- | --- |
| D1 | 后端技术栈 | **NestJS 12 + Fastify + TypeScript**（Node v24，无需 JDK） |
| D2 | 架构形态 | **网关独立进程 + 业务域聚合单体多模块**（2 个进程） |
| D3 | 首版范围 | **M0 + M1**：先打通主链路 + 车辆仿真，视觉后置 |
| D4 | 地图实现 | **自绘矢量路网**（离线、前后端共用 `map.json`） |
| D5 | 数据库 | **SQLite + `node:sqlite` 内置驱动**（零安装零编译） |
| D6 | 服务注册发现 | 不引入注册中心（两进程无需） |
| D7 | 业务控制台 | 极简 `/ops` 页（造场景 + 数据重置 + 只读看库），且**不得使用后台管理风格** |
| D8 | 前端图表 | **ECharts 6 + 自定义 ToC 主题**，禁止默认报表样式 |
| D9 | 视觉风格 | **ToC 消费级，明确禁止后台管理风格**；用 `taste-skill` 约束 AI 产出 |

> 以上决策的前置说明见 §0 决策记录。若后续要调整，直接改 §0 与本节，保持单一事实来源。

## 16. 设计资产：taste-skill 集成

为对抗"AI 生成界面的模板味"，本项目已引入开源设计技能库 **taste-skill**（MIT 协议，仓库 91k stars），落在 `robotaxi-demo/skills/`，版本与用法详见 **`03-设计资产-taste-skill说明.md`**。

**它解决的问题**：AI 写前端会稳定地输出同一套廉价模板（AI 紫渐变、三等分特性卡、满屏 em dash、div 假截图、Inter 字体、KPI 数字墙）。taste-skill 把"高级感"拆成可执行的硬规则与禁令，并在交付前跑一遍机械化的 Pre-Flight 检查。

**各子技能在本项目的分工**：

| 子技能（目录） | 安装名 | 本项目用在哪 |
| --- | --- | --- |
| `taste-skill` | `design-taste-frontend` | 总纲：Design Read、三个旋钮、反 AI 味禁令、Pre-Flight 清单。**`/about` 介绍页与登录页**直接用它的落地页范式 |
| `soft-skill` | `high-end-visual-design` | **主力**：消费级高级感（柔和对比、大留白、premium 字体、弹簧动效），贴合"ToC 要好看"的核心诉求 |
| `minimalist-skill` | `minimalist-ui` | **行程页 / 订单页**这类信息较多但不能有后台味的界面 |
| `brandkit` | `brandkit` | 品牌色板、字体、logo 方向 |
| `imagegen-frontend-mobile` | `imagegen-frontend-mobile` | 生成移动端页面参考图（移动优先） |
| `image-to-code-skill` | `image-to-code` | 「先生成参考图 → 再分析 → 再写代码」的流水线 |
| `redesign-skill` | `redesign-existing-projects` | M2 视觉打磨阶段，对已有页面做审计式改造 |
| `output-skill` | `full-output-enforcement` | 防止 AI 交付半成品（留 TODO 占位） |

**使用纪律**：

- `taste-skill` 主技能自述适用范围是"landing pages / portfolios / redesigns，**不是 dashboards、不是多步产品 UI**"。本产品属于多步产品 UI，因此**只取其设计工程法则与禁令，不套用其落地页区块骨架**（sticky-stack、horizontal-pan 等）。
- **em dash（`—`）禁令**适用于**所有面向用户可见的 UI 文案**（含中文界面里的破折号，改用逗号 / 句号 / 括号 / 分行）。内部设计文档不受此限。
- 三个旋钮的取值固定为 §8.1 的 `7 / 6 / 4`（安全类页面单独降档），不允许各页面自行改动。
- 交付前必须过一遍 `02` 文档的 Pre-Flight 检查清单。

## 附录 A：命名与文案基调

- 品牌语气：**沉稳、可靠、不卖萌**。参考 Apple / 蔚来的表达方式。
- **UI 文案禁用 em dash（`—`）与 en dash（`–`）**，中文场景改用逗号、句号、括号或分行。
- 关键文案示例：
  - 匹配中：「正在为您匹配最近的无人车」（而非"搜索司机中"）
  - 车辆到达：「车辆已到达，看到尾号 3721 的车，请上车」
  - 行程中：「车辆正在礼让行人，预计延误 20 秒」
  - 结算：「本次行程 3.2 公里，减少碳排放约 0.4kg」
- 禁用词：赋能、闭环、抓手、无缝、颠覆、下一代、极致体验。

## 附录 B：种子数据建议

- POI：30~50 个（机场、高铁站、商圈、写字楼、医院、大学、公园、住宅小区），覆盖全部演示路径。
- 车辆：8 台（3 种车型），初始分布在地图不同区域。
- 用户：3 个测试账号（含 1 个有历史订单、1 个新用户）。
- 历史订单：预置 12 条已完成订单（含轨迹与费用明细），同时服务于订单列表与 **ECharts 出行足迹图表**（月度柱状、类型环形、时段分布），保证图表一打开就有真实形状的数据，而不是几条假直线。
- 数据要求：**避免"假完美数字"**（不要 `50%`、`100%`、`123456`），用有机数字如 `47.2%`、`3.2 公里`、`¥18.6`。
