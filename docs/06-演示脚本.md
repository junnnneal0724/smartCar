# 06 · 演示脚本

> 面向"要用这个 Demo 给别人讲一遍"的场景。全流程约 8 分钟，可以按时间砍成 3 分钟版。
>
> 演示前请先执行一次重置，保证从"车辆正在赶来"开始：
>
> ```powershell
> pnpm reset:db     # 删库，下次启动自动重建
> pnpm dev
> ```
>
> 或者在后端已经跑着的情况下，打开 `http://127.0.0.1:5173/ops` 点「重开一趟行程」。

---

## 一句话定位（开场用）

> 这不是一个叫车 App。手机上的叫车流程已经被解决得很好了。
> 我们要做的是**乘客拉开车门、坐进去之后的这二十分钟**：
> 车里没有司机，面前只有一块屏幕，那么这块屏幕应该回答什么问题。

---

## 3 分钟版（只讲一条主线）

| 时长 | 屏幕 | 说什么 |
| --- | --- | --- |
| 0:00 | `/waiting` | 车正在赶来。注意地图上的车是沿真实路网走的，不是贴上去的图标 |
| 0:30 | `/welcome` | **一单一车，所以最重要的一次确认是"这是我叫的车"**。车牌、车内编号都在这儿 |
| 1:00 | `/verify` | 车机是公共设备，不做登录。用手机尾号后 4 位把这段行程绑到人身上，下车即失效 |
| 1:30 | `/ready` | 出发前必须由乘客亲自按下「开始行程」。车辆不会自己走 |
| 2:00 | `/trip` | **核心一屏**。看左下角的决策气泡：每次礼让行人、等红灯、绕障，车都会解释自己在干什么 |
| 2:40 | `/summary` | 行程小结。速度曲线和费用构成 |

**3 分钟版的收尾一句话**：

> 整条动线里没有一处需要用户"管理"什么东西。这是刻意的：
> 乘客在车上只有两个诉求，一是知道我还要多久到，二是知道它刚才为什么那样开。

---

## 8 分钟版（完整动线）

### 第 1 幕：它来了（约 1 分钟）

**屏幕**：`/waiting`

- 车辆位置 2Hz 推送到前端，前端按 60fps 插值补间，所以移动是连续的
- 地图是**自绘的**：路网数据前后端共用同一份 `assets/map.json`，所以后端算出来的路径和前端画出来的路径一定重合
- 顶部状态条上写的是车辆当前所在的道路名，这个数据来自仿真引擎，不是假的

**可以顺手演示**：打开 `/ops`，把仿真倍速从 4x 调到 16x，车会明显加速赶来。

### 第 2 幕：上车确认（约 1.5 分钟）

**屏幕**：`/welcome` → `/verify`

- 一单一车意味着**不存在"上错车"之后的兜底**，所以身份核对必须在前
- 点「车牌对不上」会就地展开，给出呼叫远程安全员和开门下车两条出路。
  这里刻意**不用弹窗**：弹窗会把乘客困在一个只有"确定"的对话框里
- 校验用屏幕数字键盘，因为车机没有物理键盘，弹出系统输入法会遮住半个屏幕
- 输错会抖动并就地报错；校验过期会提示重新叫车

**要讲的设计点**：校验通过后 token 存在 `sessionStorage`，与这一段行程绑定。
行程 `COMPLETED` 之后 token 立刻失效，下一位乘客打开屏幕看到的只有"等待中"。

### 第 3 幕：出发前（约 1 分钟）

**屏幕**：`/ready`

- 三项检查（安全带 / 随身物品 / 确认目的地）必须全部勾选，「开始行程」才可用
- 未勾选时按钮**禁用并说明原因**，而不是点下去弹一个「请先系好安全带」
- 右侧行程卡始终在，乘客随时能知道目的地和预估费用

**要讲的设计点**：为什么把"开始行程"交给乘客而不是自动开始。
因为无人驾驶车里，"我确认可以走了"这个动作是乘客唯一能行使的控制权，
把它拿掉会让整段行程变成"我被一台机器带走了"。

### 第 4 幕：行程中（约 2 分钟，重点）

**屏幕**：`/trip`

先让车自己跑一会儿，等决策气泡自然出现。

- 气泡出现的时机是车辆行为真的发生了变化（礼让行人、等红灯、绕障），
  不是定时轮播的假动效
- **不出弹窗、不发声、不遮挡任何操作**，只在视野边缘说一句人话
- 点开气泡能看到完整解释

然后点右侧的「这趟车都经历了什么」进 `/trip/explain`：

- 顶部一句话结论，例如"这趟行程里，有 xx% 的时间在等红灯和礼让行人"
- 横向堆叠条展示时间分配；点任一段展开看解释
- 下方时间线按顺序列出每一次决策

**要讲的设计点（这是整个产品最想讲的一件事）**：

> 乘客对无人驾驶的恐惧，绝大部分不是怕它开不好，而是**怕自己看不懂**。
> 所以"解释"不是一个附加功能，它是这个产品的第一功能。

### 第 5 幕：车上能做的事（约 1.5 分钟）

**屏幕**：`/cabin`、`/stop`、`/help`

- `/cabin`：场景一键切换。小憩 / 办公 / 放松，以及给容易晕车的乘客准备的「舒缓」。
  分温区控温、风量、座椅加热通风、氛围灯、亮度、音量、遮阳帘
- `/stop`：**分级停靠**。「前方下车」是柔和的次要操作；「紧急停车」是唯一的危险色区域，
  并且必须长按 1.2 秒。这个设计是刻意的：紧急停车是个会造成后车风险的强操作，
  不应该和"下一站下车"长成一个样子
- `/help`：帮助永远在底部功能条最右侧，**从任何页面一次点击可达**。
  接通安全员之后底部是一排预置问题按钮而不是输入框，因为车机上打字是折磨
- 隐私区明确写出摄像头、麦克风、位置各自的用途与保留期限

**要讲的设计点**：为什么不做娱乐（视频、音乐）。
车内屏幕的第一职责是安全与行程信息，娱乐会挤占掉决策解释的位置。
这一条写进了产品的取舍记录里，是主动砍掉的，不是没来得及做。

### 第 6 幕：到站与收尾（约 1 分钟）

**屏幕**：`/arriving` → `/alight` → `/summary` → `/rate` → `/farewell`

- `/arriving`：剩余距离、下车点、遗留物品清单
- `/alight`：**车没停稳时开门按钮是禁用的，并且会直接说明原因**。
  这一条是安全底线：宁可让人多等两秒，也不能给一个"按了没反应"的按钮
- `/summary`：速度曲线 + 费用构成环形图。这里也是全项目唯一允许出现图表的地方
- `/rate`：只有星星和标签，没有文本输入框
- `/farewell`：明确告知"个人数据已从本屏幕清除"，30 秒后自动回到待机屏

**收尾一句话**：

> 这块屏幕是公共的，所以它对数据的处理必须比手机更克制。
> 送别页那句"已清除"不是文案，是这套流程真的在做的事。

## 演示前检查清单

- [ ] `pnpm dev` 已启动，浏览器打开 `http://127.0.0.1:5173`
- [ ] 窗口按 1920×1080 横屏，按 F11 全屏（这是车机的目标分辨率）
- [ ] 已经在 `/ops` 点过「重开一趟行程」，屏幕上是从"车辆赶来"开始
- [ ] 校验码固定是 `1234`（默认乘客林小满 13800001234 的手机尾号），不必去查
- [ ] 网络断掉也不影响演示（地图、路网、图表全部本地）
- [ ] 如果投影仪偏亮，在状态条右上角切成浅色主题；观众离得远就打开大字模式

## 常见提问与回答

**"为什么不用高德/百度地图？"**
因为路网是合成数据，铺在真实底图上反而对不上。而且深色车机地图对路面颜色、
路线辉光的要求，第三方底图改不动。自绘还有一个好处：前后端共用同一份路网文件，
后端算的路径和前端画的路径不可能不一致。

**"真的没有数据库要装吗？"**
没有。用的是 Node 24 内置的 `node:sqlite`，数据库就是一个文件，零安装零原生编译。
删掉它下次启动会自动重建并灌好演示数据。

**"后端为什么不是微服务？"**
本地 Demo 没有高并发需求，拆成微服务只会增加启动步骤。
现在的结构是一个网关进程加一个业务进程：网关负责转发和 SSE 透传，
业务侧按领域分了 7 个模块（车辆、行程、会话、座舱、帮助、实时、仿真），
模块边界是按微服务的方式划的，真要拆的时候拆得动。

**"代码里的破折号为什么一个都没有？"**
这是一条硬性文案规范，来自设计技能 `taste-skill` 的约束。
用户可见的文案里禁止出现破折号，要停顿就用逗号或句号。
文档里不做这个限制。
